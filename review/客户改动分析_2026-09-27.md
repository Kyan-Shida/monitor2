### 一期范围需要特别核对

客户将 `calendar`、`dispatch-log`、`rules`、`routes`、`standards`、`services`、`analytics`、`media`、`users`、`quick` 隐藏于侧栏，并从导航中移除了 `objects`。隐藏不代表路由或实现全部删除，例如临时任务还可通过工作台的“新建任务”进入。

原设计要求所有一期页面从菜单可进入，因此不能仅依据客户版 README 的“未实现占位”说明认定这些页面可取消。应对照 `main` 保留的 `docs/source-v1.4.txt` 和 `docs/coverage.md`，确认哪些改为业务内置入口、哪些需要恢复。新增工单、SLA、多机型、轨道/充电资源、排班资质等也应与一期范围重新核对。

## 已确认的问题

### 1. P1：本地持久化函数无限递归，所有操作无法保存

位置：[`src/data/store.tsx`](../src/data/store.tsx#L54)，54–59 行。

`persist(n)` 内再次调用 `persist(n)`，没有执行 `localStorage.setItem`。递归耗尽调用栈后异常被 catch 吞掉，界面仍显示成功，但记录不落盘。影响业务操作、角色切换、重置；刷新会回到种子数据或旧缓存。

浏览器复现：干净浏览器进入工作台 → 用户菜单切换为非管理员 → 查询 `inspection-v14-prototype`，键不存在 → 刷新后恢复管理员。该行为已实际验证，不只是静态推断。

建议：在容错函数内写入序列化状态，增加“保存→刷新→状态保持”验证。

### 2. P1：标准构建失败

位置：`src/data/types.ts:271`、`src/data/seed.ts:218`、`src/data/store.tsx:22`、`src/pages/Scheduling.tsx:589`。

实测 `npm run build` 失败，输出三处错误：

1. `State.schema` 声明为 `3`，种子数据使用 `5`。
2. `store.tsx` 升级为 `schema: 5` 后断言为 `State`，类型不兼容。
3. 外层分支已经限定 `page === "dispatch"`，内部仍判断 `page === "queue"`。

单独 `npx vite build` 通过，只表示打包器可以转译，不能替代标准构建与类型检查。客户 README 已承认这些错误，但它们仍是实际交付阻断。

建议：统一 schema 类型/常量/迁移路径，删除不可达比较。迁移目前只覆盖 schema 1/2/5，schema 3/4 缓存会回退 seed，修复时需同时确认旧数据保留要求。

### 3. P2：队列改派后缺少明确的继续派单入口

位置：`src/data/engine.ts:632`、`src/data/engine.ts:666`、`src/pages/Scheduling.tsx:173`、`src/pages/Scheduling.tsx:610`。

`REASSIGN` 与 `PREEMPT` 仍把新任务设为“已分配”，队列只给“待执行/暂停”提供 START，原 DISPATCH/RECEIPT 按钮已移除。队列完成改派后，缺少明确的下一步派单入口。

这不是全局死锁：调度页底部“任务分配与接收记录”仍包含已分配任务，可点击“调度决策”重新选中，再通过上方派单继续。脚本观察：ENQUEUE → REASSIGN 后直接 START 报“任务尚未接收”，再次 ENQUEUE 则恢复“待执行”。问题是跨页继续路径不够明确，而不是状态机无法继续。

建议：队列改派后提供“继续派单”或“返回调度”入口，并明确任务仍待派单；抢占后也提示下一步，避免用户误以为任务已可执行。

### 4. P1：新增一次派单链路将版本不匹配任务标记为已接收待执行

位置：`src/data/engine.ts:571`、`src/data/engine.ts:598`。

ENQUEUE / DISPATCH_NOW 在机器人忙碌时过滤掉地图/点位版本不匹配约束，并立即把任务设为“待执行”。这与原 ASSIGN 允许版本不匹配“预分配”、但 DISPATCH 必须核对版本的语义不同：现在界面会表示任务已下发接收，即使版本未匹配。

脚本复现：将执行中 R01 改为 m2/p6，给它派要求 m3/p7 的 T010，任务仍进入“待执行”。后续 START/TICK 的版本检查仍存在，因此不能据此宣称错误版本任务已真正执行；问题是前置状态与下发语义不一致。

建议：不匹配时保留预排/待同步状态，或禁止正式下发直到版本激活并收到接收确认。机器人自主寻找目标，不意味着可以跳过地图版本与任务接收核对。

### 5. P2：排队任务没有自动续执行，队列调序也失去常规入口

位置：`src/data/engine.ts:588`、`src/data/engine.ts:719`、`src/data/engine.ts:829`、`src/pages/Scheduling.tsx:189`。

派单提示“等待当前任务结束后执行”，但 TASK_FINISHED / TICK 结束时只将机器人置为空闲，没有选择或启动下一项。脚本复现得到“R01 空闲、current=null、T010 仍待执行”，实际需要手工开始。

另外，新入列任务直接变为“待执行”，REORDER 与“置于队首”只支持“已分配”；未来时间轴也只在调度页渲染，并传入恒为 false 的 draggable。正常新入列任务无法通过原有队列方式调序。

建议：明确自动续执行还是人工确认续执行，并使文案与实现一致；若保留已接收队列调序，补充撤回/重排/确认协议及可操作入口。

### 6. P2：一键返航留下活跃人工接管会话，状态相互冲突

位置：`src/data/engine.ts:1070`。

RETURN_HOME 终止任务、清除 current 并直接设置机器人“充电”，但没有释放或结束接管会话。脚本复现：TAKEOVER → CONTROL_ACK → RETURN_HOME，得到“机器人充电、任务取消、会话仍已接管”。之后仍可从会话路径发遥控指令，并影响恢复核对。

建议：返航时限制活跃会话，或执行统一退出/释放过程；“返航中”和“已到位充电”也应区分，避免下发指令即认为已到达充电位。

### 7. P2：角色“分管厂区”数据范围目前只是声明

位置：`src/data/roles.ts:121`、`src/pages/MonitorCockpit.tsx:50`、`src/data/metrics.ts:51`。

非管理员被声明为“分管厂区”，但没有分管厂区 ID；Store 仍提供全量 State，驾驶舱默认“全部区域”，业务列表也没有统一按角色裁剪。当前真正生效的是菜单可见性和部分按钮权限，不是数据范围。

建议：若只演示角色菜单，应明确说明；若演示数据权限，应增加角色区域绑定及统一范围过滤，避免评审认为数据隔离已实现。这是原型行为与文案的问题，不把纯前端原型当作生产鉴权系统评判。

原测试的两项不通过分别是“页面定义由 38 增到 41”和“新增爬楼能力要求导致旧改派样例被拒绝”，属于需要更新测试夹具/预期的变化，未将其直接列为故障。通过项覆盖地图导入/验证/发布、自主执行结果、告警复查关闭、接管释放恢复、版本错配/迟到回执、结果证据不覆盖、无有效结果的任务结束判定和临时任务原子动作能力限制。

诊断脚本可在本分支运行：

```sh
npx --package tsx tsx review/customer-state-check.ts
```

脚本记录现有问题的实际状态，不是“业务应当如此”的通过测试。原仓库的测试文件和 npm test 已被客户删除；本次没有完整遍历 47 个路由，也没有重新生成并全面测试离线版，不宣称全部页面/所有新增业务可用。

## 建议合并顺序

1. 先修复持久化和标准构建，恢复状态测试入口。
2. 优先核对一次派单、改派、抢占、版本同步与续执行闭环。
3. 保留客户的导航归并、来源返回、页面标签、工作台、指标口径和离线导出等成果。
4. 对新增多机型/轨道/工单/SLA/角色范围明确一期边界；把示例、占位和真正可操作功能区分清楚。
5. 如继续开展外部评审，恢复 main 中的“评审意见”功能与多人 JSON/Markdown 汇总能力；客户版已无对应入口。

结论：客户明显加强了业务展示和交付体验，但工程可构建性、本地状态保留及新调度链路存在实质问题，当前适合作为独立评审分支，不宜未经修复直接覆盖 main。
